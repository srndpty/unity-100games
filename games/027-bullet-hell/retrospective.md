# 027 振り返り

## 新たに学んだ点

弾道 DSL の解釈（`ScriptParser`）・弾の生成（`PatternPlayer`）・弾の更新（`BulletPool`）を分けると、それぞれを別々にテストでき、弾幕は台本を差し替えるだけで変えられた。弾の位置を 1 px = 2^30 の整数で持ち、速さ × 整数の cos 表をそのまま足すと、直進・等加速の弾は閉じた式とちょうど一致し、表を整数のテイラー展開で作れば .NET と Mono で同じ試合になった。大量の弾は固定容量の SoA と 1 つの Mesh で、Core の 1 Tick も描画の更新も 2048 発で 0.4 ms 以下・割り当て 0 にできた。

## 想定との差

Mono の `GC.GetAllocatedBytesForCurrentThread` は常に 0 を返し、割り当ての検査が何も確かめていなかった（4096 バイトを割り当てて計数が増えるかを確かめて気づいた）。`Mesh.SetVertices(配列, 開始, 長さ)` は頂点の数を縮め、弾が 1 発も描かれなかった。自動操縦は「弾から最も離れる」を優先するとほぼ全弾幕が時間切れになり、6 つ目の弾幕は発射器を 1 つずつ外して、ゆるく曲がる輪が真下を塞いでいると突き止めた。レビューでは、座標を縮める掃引が「接するだけ」を触れたと判定すること、Prefab の検査が幕の配置を見ていないこと、ボムの重複した押下を指摘された。

## 次回の改善点

計測やテストの仕組み（割り当ての計数・描画）は、確かめたい対象の前に「わざと起こしたら検出できるか」を 1 度確かめる。桁あふれを避ける近似は境界の規則（ちょうど接するなど）を壊しうるので、近似を最終判定にせず、厳密な判定へ回す。描画の不変条件（幕の位置など）は、生成と検査が同じ関数を使うように最初から書く。
