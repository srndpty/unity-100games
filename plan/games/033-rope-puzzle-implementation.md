# 033 ロープ物理パズル 実装計画

## Context

- 033 ロープ物理パズル（難易度3・Phase 2）が未着手。仕様書 [plan/games/033-rope-puzzle.md](./033-rope-puzzle.md) の中心課題は「**ロープ拘束を Joint または自前制約で実装**」、重点は「**操作と物理更新を分離**」。In scope：10 問・吊り下げロープ・指示箇所で切断して物体を目標へ・リセットと手数記録・タイトル→説明→結果→再プレイ。Out of scope：柔体の精密シミュレーション、追加ギミック多数。
- 題材固有テスト：切ったロープは拘束を失う／同一ロープの重複切断安全／成功判定は物体到達時のみ。完了判定：10 問を解ける、同じ初期条件で概ね再現可能。
- ユーザーと決めたこと：
  - **自前の固定小数点制約**：Core で Verlet＋距離拘束を整数で解く（Unity の物理は使わない）。.NET と Mono で最終ハッシュを一致させ、10 問の解答手順を dotnet テストで再生して「解ける」を保証する。
  - **マウスでなぞって切る**：押したままのドラッグの線分が横切ったロープを切る。1 回のなぞりで複数本切れたら手数は本数ぶん。
  - **失敗＝画面外への落下またはトゲへの接触**（その問をやり直し）。他の要素は固定の壁・台だけ。
  - **順に解放＋問ごとの最少手数**：問題選択は解いた次の問まで。各問の最少手数は起動中だけ記録。10 問クリアで結果画面。

作品名はオリジナル（仮）：**DEWDROP SNIP**（吊るした露玉を切って花の器へ落とす）。参考作品の名称・素材・演出は使わない。
この計画は着手時に `plan/games/033-rope-puzzle-implementation.md` として保存し、各セッションの結果を追記する（025〜032 と同じ）。

## セッション1：ルール表（README に固定）と Core / App

### ルール表（要点）

| 項目 | 採用ルール |
|---|---|
| 時間 | 60 Tick/秒。物理は 1 Tick に 1 回進め、浮動小数点を使わない |
| 座標 | 1 m = 256 単位の整数（`Vec2i`）。盤は 16 × 9 m（4096 × 2304）。y は上向き。近い組の値が `Sweep.FirstLimit`（16384）に収まる |
| 点 | ロープの節点と露玉は Verlet 点（現在位置・前の位置）。速さ＝位置の差 × 減衰（整数の比、例 255/256）。重力は 1 Tick あたりの整数加速度。1 Tick の移動量は設定の上限で切り詰める |
| ロープ | 支点（固定）→ 節点 N 個 → 露玉の鎖。節の自然長は問題データのロープ長 ÷ 節数（整数）。距離拘束は「伸びたときだけ縮める」（たるみは許す）。逆質量で配分（支点 0・節点 1・露玉は設定の重さ）。拘束の反復は設定の固定回数で、順序は問題データの順 |
| 平方根 | `IntMath.Sqrt`、補正は `IntMath.RoundDiv`。長さ 0 の節は補正しない |
| 切断 | なぞりの線分（前フレームのマウス位置 → 今の位置、整数化）が節の線分と交差（外積で厳密判定、端点に触れたら交差）したらそのロープを切る。**1 本のロープは 1 回だけ切れる**：切れたロープの断片は以後切れず、手数も増えない。同じなぞり・同じ Tick で同じロープに 2 回触れても 1 回 |
| 切った後 | 交差した節を境に 2 つの断片に分ける。支点側は支点から垂れ下がり、露玉側は露玉から外れて自由に落ちる（画面外に出たら消える）。**露玉はそのロープの拘束を以後受けない**。断片は当たり判定を持たない（描画だけ） |
| 適用の順序 | 入力（切断の命令）は Tick の境目でだけ反映：**切断 → 積分 → 拘束の反復 → 壁の押し出し → 接触判定（目標・トゲ）→ 落下判定**。操作は命令の列として渡り、物理の途中に割り込まない |
| 露玉 | 円（半径は設定）。ロープの節は壁と衝突しない（通り抜ける。問題をそう作る） |
| 壁・台 | 軸に沿った長方形。露玉が重なったら最も浅い方向へ押し出し、その軸の速さを 0（前の位置を合わせる）。1 Tick の移動量の上限 < 壁の最小の厚さ を設定の検証で保証（すり抜けない） |
| 目標・トゲ | どちらも円。露玉の Tick 中の軌跡（始め → 押し出し後の終わり）で `Sweep.First` を取り、最も早く触れた物で決める。**目標に触れたら成功、トゲなら失敗**。同時刻なら失敗を優先 |
| 成功 | 目標に触れた Tick にだけ成功。ロープで吊られたまま目標に触れても成功（到達で判定）。それ以外の手段（時間経過・全ロープ切断）では成功しない |
| 落下 | 露玉の中心が盤の外（下・左右）へ出たら失敗 |
| 手数 | 切ったロープの本数。リセット（R）はその問の初期状態に戻し手数 0。成功時の手数を問ごとの最少手数と比べて記録（起動中のみ） |
| 終了後 | 成功・失敗の後の Tick と切断は状態を変えない（失敗の表示から R で再挑戦、成功から次へ） |
| 乱数 | 使わない（同じ問・同じ命令列なら同じ結果） |

### 問題データ（`Assets/Game/Data/Puzzles.txt`、TextAsset）

- 1 問 = 名前・案内文・露玉の初期位置・ロープ（支点・長さ・節数）の列・壁・トゲ・目標。行指向のテキスト（例：`rope 1024 2048 640 12`）。
- Core の `PuzzleBook.Parse` が検証：10 問ちょうど、各問にロープ 1 本以上・目標 1 つ、座標が盤の内、ロープ長 ≥ 支点と露玉の距離（初期に伸びていない）、節数の範囲、露玉が初期に壁・トゲ・目標と重ならない、壁の厚さ ≥ 移動量の上限。dotnet のテストも同じファイルを読む。
- 10 問は 1〜2 本の易しい問から、順序・時機（振り子の揺れ）が要る問、壁で受けて転がす問、トゲの間を落とす問へ。

### Core（`Assets/Game/Core/`）

- `RopeConfig`：重力・減衰・拘束の反復回数・露玉の半径と重さ・移動量の上限・盤の大きさ。公開フィールド＋検証（整数なので有限の検査は不要、範囲と派生条件：上限 < 壁の最小の厚さ、値が `FirstLimit` に収まる）
- `Verlet`（点の配列、SoA）・`Rope`（節の範囲・自然長・切れたか）・`RopeSolver`（積分・拘束の反復。状態を持たない関数）
- `Segment`：線分の交差（外積、long で厳密）。なぞりと節の判定
- `Obstacles`：壁の押し出し、目標・トゲの接触（`Sweep.First`）
- `Puzzle`・`PuzzleBook`（データと検証）
- `PuzzleRun`：1 問の試合。`Cut(Vec2i from, Vec2i to)`（命令を Tick の境目に積む）・`Tick()`・`Reset()`・`Clone()`・`Hash()`・`Outcome`（進行中／成功／失敗と理由）・`Moves`。ハッシュに全点の位置と前の位置・切れたロープ・断片・手数・Tick・結果を含める（022）
- `Progress`：解放済みの問と問ごとの最少手数

### App（`Assets/Game/App/`）

- `SnipFlow`：Title / Select / Playing / Paused / Cleared(問) / Failed(問) / Result(全問)。時間は引数で受け取り固定 Tick へ変換（フレーム単位の Tick 上限、017・022）。マウスの押下・移動・解放とキーは受け取った順の 1 本の列（012）で、なぞりの線分は**その入力が届いた時刻を含む Tick**の境目で切断命令になる（022 の時刻付き入力）。フォーカス喪失でなぞりを打ち切り一時停止、復帰直後のクリックは捨てる（010）
- `SwipeTracker`：押している間の前の点を持ち、離す・フォーカス喪失・問の切り替えで捨てる。押した瞬間の点だけでは切らない（線分が要る）
- 画面座標 → 盤の整数座標の変換は Unity 側で行い、App には整数で渡す

### 解答手順と最少手数

- `Assets/Tests/Core/Data/Solutions.txt`（テスト側、本体に解答機能は入れない、012）：問ごとに `Tick: x1,y1 -> x2,y2` のなぞりの列。撮影台本も同じ形式の手順を Unity 層に持つ。
- `[Explicit]` の探索テスト：各問でロープを切る順序 × 時機（数 Tick 刻み）を総当たりし、解けることと最少手数を求めて README に記録（問の目安として表示）。

### テスト（題材固有を優先）

- **切ったロープは拘束を失う**：切った後の露玉の軌道が、そのロープを最初から持たない問の同じ Tick 以降の軌道と一致（両方の状態ハッシュ・位置を比較）。支点側の断片は支点から垂れ、露玉側の断片は露玉と距離が開いていく
- **同一ロープの重複切断安全**：同じなぞりで同じロープの 2 節を横切る／切れたロープの断片をなぞる／同じ Tick に 2 回の命令／成功・失敗の後の切断 → いずれも手数・状態が変わらない。別のロープは独立に切れる
- **成功判定は物体到達時のみ**：目標の手前で止まる配置では何 Tick 進めても成功しない／全ロープを切っても目標を外れたら失敗（落下）／吊られたまま目標に触れた Tick に成功／目標とトゲに同じ Tick に触れたら触れた時刻の早い方、同時刻は失敗／速い落下で目標を通り過ぎる軌跡でも成功（掃引）
- **10 問を解ける**：解答手順を全問で再生して成功。各問は何も切らずに十分な Tick 進めても成功しない（自明でない）
- 物理：静止した吊り下げで節の伸びが上限以内に収まる・長い通し（例 10 万 Tick）で位置が盤と移動量の上限を超えない、壁の押し出しで露玉が壁の中に残らない（厚さの境界値）、線分の交差を素朴な参照実装（有理数の交点）と乱数で照合、端点に触れる・平行・重なりの境界
- 再現性：同じ命令列で同じハッシュ、固定の通し（全 10 問の解答）の最終ハッシュを .NET と Mono で照合、「今は同じでも以後が分かれる」組（前の位置だけ違う）で違うハッシュ
- 共通：状態遷移（タイトル→選択→進行→成功→次の問→…→結果→再プレイ、失敗→R）、未解放の問を選べない、負テスト（範囲外の設定・壊れた問題データ 10 通り程度・重複イベント）、リセットで初期状態のハッシュに戻る

## セッション1の結果（2026-11-24）

- ルール表は [README](../../games/033-rope-puzzle/README.md) の「採用ルール」を正とする。
- Core：`Board`・`RopeConfig`、`Puzzle`・`PuzzleBook`（問題データと検証）、`Segment`（線分の交差）、`PuzzleRun`（Verlet と距離拘束・切断・壁・接触・落下・ハッシュ・複製）、`Progress`（解放と最少手数）、`CutPlan`（解答の手順と、ロープだけを横切るなぞり）。App：`Intent`・`SnipFlow`・`Snipper`。
- 問題集 `Assets/Game/Data/Puzzles.txt`（10 問）と解答 `Assets/Game/Data/Solutions.txt`。
- Core 67 件・App 19 件が .NET で、パッケージを含む 148 件が Mono で通った。全 10 問を解いた最終状態のハッシュ `0x10E40AFC` が一致。
- 計画との差：
  - 座標の単位を 1 マス = 4096 から 65536 にした。4096 では露玉への補正が丸めで 0 になる不感帯ができ、振り子が真下から外れて止まった。
  - そのため `Sweep.First` の値の上限を超えるので、接触は `Sweep.Touches`（厳密）で判定し、「目標とトゲは触れた時刻の早い方」を「同じ Tick に両方なら失敗」に変えた。
  - 節点の逆質量を 8 から 32 にした（ロープが重いと振り子の揺れがすぐ消えた）。反復は 16 から 24（伸びが約 6% から 4%）。
  - `Progress` は Core に、`Snipper` は App に置いた。解答の手順は撮影でも使うので `Assets/Game/Data/` に置く（画面には出さない）。
  - 問の設計は、切る順序と時機の総当たり（作業用の一時的な探索ツール、12 Tick 刻み）で解けることと手数を確かめた。「すき間」と「仕上げ」は最初の配置では解けず、配置を直した。
- 次（セッション2・3）：Unity 層（生成ドット絵・Stage Prefab・ロープの描画・なぞりの軌跡・HUD・音・シーン生成・撮影台本）と検証。
