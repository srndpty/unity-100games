# 1本あたりの標準ワークフロー

## 0. Scope Freeze

対象の`games/NNN-*.md`を読み、ルール差異、使用Unity版、データ形式、勝利条件を固定。Out of scopeに該当する要求は追加しない。

## 1. Core-first

ゲーム状態と入力コマンドを先に設計。主な状態遷移を一枚の図または簡単な表にする。最小のEditModeテストを先に書き、基本・境界・不正・多重実行を検証。

## 2. Playable

単一シーンまたは最小限のSceneにCoreを接続。操作・表示・効果音は必要十分に留め、開始/終了/リスタートを実装。

## 3. Verification

各題材の必須テスト＋共通テストを実行し、データ不変条件を確認。Windowsビルドを作り、`dev capture` でJPEG品質85のスクリーンショットを保存。ここまで通したら状態を「検証待ち」にする。

## 4. Human Play

人間が `dev run NNN` で遊び、通しプレイの可否と調整点（難易度、速度、音量、操作感など）を返す。調整して再度遊んでもらい、OK が出たら次へ進む。完成の判断は人間が行う。

## 5. Retrospective

技術的に新しかった点、発生した不具合、次なら変える設計の3点を記録。他の作品にも効く知見は `AGENTS.md` の「Unity 実装の知見」へ移す。仕様書の完了判定にチェックを付け、`progress.csv` を更新して完了。

## セッションの区切り

- 1作品1セッションを基本にする。前のセッションの会話は引き継がれないため、知見と途中経過は必ずファイル（`AGENTS.md`、`progress.csv`、作品の README）に残す。
- 大きい題材は「Core-first」「Playable」「Verification」でセッションを分ける。区切りでは、どこまで済んだかと次にやることを `progress.csv` の記録/メモに書く。

## スコープ膨張ルール

- 見た目の磨き込み・コンテンツ追加は原則として完成条件に入れない。
- Coreのテストが難しければ、抽象化を増やすより境界を見直す。
- 一作品で2日以上詰まったら、目的技術を守ったまま表現・素材・面数を小さくする。ルールの正しさは削らない。
- 継続不可能なほど大きい題材（MOBA/RTS等）は、削る機能を変更履歴に明記し、最小メカニクスの実証を優先する。
