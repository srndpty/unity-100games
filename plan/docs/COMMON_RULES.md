# 共通ルール / 完成の定義

## ゴール

100本の独立した短時間プレイ可能ゲームを完成し、ジャンル固有の実装課題を学ぶ。各題材で「最小スコープを満たした、テストできる構造」を優先し、コンテンツ量は増やさない。

## 必須3ゲート

| ゲート | 完成条件 |
|---|---|
| Core | 題材の中心ルールが仕様化され、自動テストで基本・負例を検証できる |
| Playable | 起動→操作→進行→結果→再挑戦が人間の操作で可能 |
| Verified | 題材固有のテスト、境界値、ビルド起動、実行証跡が揃う |

## アーキテクチャ原則

1. `Game.Core`：ゲーム状態、ルール、乱数、合法手、コマンド。原則としてUnityへの直接依存を避ける。
2. `Game.Unity`：描画、音響、入力、物理オブジェクト、Prefab/Scene。Coreを購読・参照する。
3. `Game.App`：画面遷移とユースケース。CoreのAPIへコマンドを発行する。
4. コアがUnity PhysX/2D物理に密接なゲームは、完全分離を強制せず「何を物理エンジンに委譲したか」を明文化する。
5. 共通パッケージは3題以上で明確な再利用価値を示したときのみ抽出。初回から大規模な抽象化をしない。

## 技術スタックの初期方針

- Unity LTS系を各作品開始時に固定し、正確なエディタ版をREADMEへ記録。100本で完全同一バージョンを強制しない。
- C#、Unity Test Framework（EditMode/PlayMode）を標準。Input Systemを基本とする。
- データ定義はScriptableObjectまたはJSON等を適材適所で採用。静的テスト容易性が低下しないようにする。
- 配布物はまずWindows向けビルドを想定。別OS/モバイル/WebGLは題材ごとの追加課題。
- Prefab/Scene/Metaをテキストシリアライズし、Version Controlを有効化。

## 再現性と品質

- 乱数はシード管理を可能にし、生成とゲーム更新の乱数を混在させない。
- 更新は可能な範囲で固定Tickとし、描画deltaTimeの変動にロジックを依存させない。
- 物理系は誤差を伴うため、同一フレームの完全一致を要求しない。計測条件と許容誤差を記録。
- 入力不正、連打、重複イベント、終了後操作、シーンリロード、オブジェクト破棄を負例として扱う。
- パフォーマンスを学ぶ題材は、対象機・画面解像度・更新対象数・計測時間・p50/p95を記録。
- ネットワーク系はレイテンシ・ジッタ・欠損条件と通信主体（サーバ/ホスト/クライアント）を固定。
- セーブがある題材は破損データ、部分データ、バージョン差をどう扱うかを明記。
- 仕様にあるゲーム固有テストで、原作依存のルール（麻雀・囲碁等）の採用範囲を事前に文書化する。

## 成果物

- ゲーム本体、README、適切な自動テスト、動作証跡、短い振り返り。
- 各題材のOut of scopeは勝手に増やさず、追加したい場合は別のStretch Goalsへ記録する。
- コミット・リリース判断は人間が行う。テスト通過だけで完成扱いしない。
